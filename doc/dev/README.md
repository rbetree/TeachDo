# `doc/dev` 文档维护规范

本目录用于维护 TeachDo 的**开发计划（Roadmap）**与相关的过程文档。为了避免“当前计划”和“历史记录”混在一起，统一遵循以下规则。

## 1. 目录结构与职责

- `doc/dev/PLAN.md`：**当前入口计划**（当前周期的 Roadmap）。只写“接下来做什么 / 为什么 / 验收标准（DoD）”，避免把实现细节写成散乱日志。
- `doc/dev/history/`：**已完成/已归档的计划快照**（以只读为主）。历史计划不在原文上继续追加新一轮需求，避免信息串台。
- `doc/dev/prototypes/`：原型/对比稿/实验性页面（不作为事实来源）。
- 其他 `doc/dev/*.md`：指南、审计、研究记录等（可更新，但不要替代 `PLAN.md` 的“入口计划”职责）。

## 2. 修改原则（必遵守）

1. **单一入口**：所有“接下来要做什么”的计划变更，优先在 `doc/dev/PLAN.md` 完成。
2. **可追溯**：修改计划类文档时必须更新文档头部的 `更新：YYYY-MM-DD`；必要时记录关联的 commit/PR。
3. **历史不可变**：`doc/dev/history/**` 默认不追加新需求；若要开启新一轮计划，应该创建新计划并归档旧文件（或在入口 `PLAN.md` 开新阶段）。

## 3. 计划文档归档规则

### 3.1 “已完成”判定（满足任一即可归档）

- 文档明确标注：`状态：DONE/已完成/已归档`（或等价表述）；或
- 所有里程碑/任务均已完成（例如全部 `[x]` / `[DONE]`），且无未决项。

> 说明：若某计划文档已被新的正式文档替代，并在正文声明“本文件为历史版本/草稿”，也应归档到 `history/`。

### 3.2 `history/` 文件命名规范（必须体现方向）

- 基本格式：`PLAN_<DIRECTION>_<YYYY-MM-DD>.md`
- 草稿/历史版本：`PLAN_<DIRECTION>_DRAFT_<YYYY-MM-DD>.md`
- `DIRECTION` 要用 **3–6 个关键词**表达计划方向/模块/改造点，使用**全大写** + `_`，避免 `PLAN1/PLAN2` 这类无语义命名。

示例：
- `PLAN_AI2PPT_TO_TEACHDO_2026-02.md`
- `PLAN_UI_UX_OPTIMIZATION_2026-02-19.md`
- `PLAN_TEACHING_MATERIAL_GLOBAL_KB_FILE_PICKER_2026-02-20.md`

### 3.3 归档操作步骤（像刚刚的归档操作一样执行）

1. 确认满足“已完成”判定（见 3.1）。
2. 按命名规范重命名（见 3.2）。
3. 移动到 `doc/dev/history/`。
4. 修正文档内引用路径（尤其是计划文档之间的互链）。
5. 自检断链（建议全局搜旧路径一次）。

## 4. `PLAN.md` 的特殊规则（入口计划滚动）

`doc/dev/PLAN.md` 永远代表“当前周期”的入口计划。

当你说“对已完成的计划文件进行归档操作”时，**必须先检查 `doc/dev/PLAN.md` 是否也已完成**：

- 若 `PLAN.md` **未完成**：只归档其他已完成计划；`PLAN.md` 继续作为入口。
- 若 `PLAN.md` **已完成**（满足 3.1 的判定）：必须执行“换新入口”流程：
  1. 将当前 `doc/dev/PLAN.md` 移动并重命名到 `doc/dev/history/PLAN_<DIRECTION>_<YYYY-MM-DD>.md`；
  2. 在原位置重新创建新的 `doc/dev/PLAN.md`，用于下一期计划（并在顶部链接到上一期归档）；
  3. 确保仓库仍能从 `doc/dev/PLAN.md` 导航到历史计划。

### 4.1 新一版 `PLAN.md` 最小模板

```md
# TeachDo 开发计划（当前）

> 更新：YYYY-MM-DD
> 上一版计划归档：`doc/dev/history/PLAN_....md`

## 0. 文档说明

## 1. 当前状态（简述）

## 2. 后续里程碑（建议）
```
